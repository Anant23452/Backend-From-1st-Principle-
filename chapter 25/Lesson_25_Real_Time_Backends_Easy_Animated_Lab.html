FROM FIRST PRINCIPLES · INTERACTIVE EDITION

What if the backend could tell the browser something right now?

Rahul changes an internship listing. Priya is already looking at the page. Follow the update from PostgreSQL to Priya without manually refreshing, and learn where it can get lost.

Before any technical term

Imagine a classroom noticeboard. If the teacher changes the exam schedule, everyone with an old paper copy still has old information. Real-time backend communication is simply a set of ways to tell them that something changed.

The important question: Does the browser keep asking, wait for an answer, or stay connected to a stream?

Memory: Saving a change and delivering the change are two different jobs.

What you can do

Change polling intervals, cause disconnects, watch missed events, explore the HTTP upgrade, add a second server, compare Pub/Sub and durable replay, and complete the quiz.

Everything is a teaching simulation. It does not open a real socket, perform network requests, or connect to Newbert.

Polling

Everyone asks repeatedly. Simple to build, but a short interval creates lots of requests even if nothing changed.

SSE or WebSocket

Connected browsers receive events when they occur. A standing connection uses memory and sockets, but avoids repeated empty polls.
