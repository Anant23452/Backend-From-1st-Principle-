The first-principles question

Why repeat an expensive operation if its answer is already available?

Caching stores some reusable data or completed computation near where it is needed. A HIT returns that answer; a MISS does the expensive work and may store a copy for later.

HITReuse workMISSGet originalTTLFreshness windowEVICTFree memory
How to remember it

Your fast revision notebook

Your textbook is the source of truth. Your revision notebook contains only the most useful facts. Looking up a fact in the notebook is a cache hit; reopening the textbook is a miss.

When your textbook changes, the notebook can be stale unless you update it. This is the central difficulty of caching.

What caching actually means

FROM THE LESSON

Caching keeps a useful subset of data or precomputed work in a faster place so future requests spend less time and effort. Cache what is likely to be reused, not everything. The original store remains the authority.

  • Every cache trades extra storage and coordination for faster repeated work.
  • A cache is not necessarily Redis: a CPU cache, DNS cache, browser cache, or CDN all fit the same principle.
  • First-principles question: What expensive work are we avoiding?
SIMPLE WAY TO REMEMBER

Think of your handwritten exam revision sheet: a compact, easy-to-reach subset of an enormous textbook.

ADDED ENGINEERING DETAIL

The cached copy can become stale. Decide what freshness means before choosing a TTL.

Google Search: cache a costly result

FROM THE LESSON

The teacher illustrates caching using common searches such as weather. Crawling, indexing and ranking involve substantial infrastructure. Repeated queries can benefit from reusing cached or precomputed results.

  • Cache hit: an eligible result already exists, so skip the expensive operation.
  • Cache miss: compute or retrieve the result and optionally save it for later.
  • Search results might vary by location, time, query, language, or user context; the cache key must represent every important variation.
SIMPLE WAY TO REMEMBER

If many students ask for the same internship category, Newbert can cache a safe, nonpersonalized listing.

ADDED ENGINEERING DETAIL

Real search engines have many specialized caches; this is an illustration, not a claim that all Google searches use one simple Redis cache.

Netflix: CDN and regional copies

FROM THE LESSON

The teacher uses video streaming to explain content encoding (1080p, 720p, 480p) and delivery through geographically distributed edge servers. A CDN holds useful copies closer to viewers, instead of repeatedly serving distant origin machines.

  • Origin: the authoritative source of the media asset.
  • Edge / PoP: geographically distributed place serving content near users; a PoP can contain multiple edge servers.
  • Not every region caches every movie, resolution, or piece of content. Popularity, geography, cost, and demand influence placement.
SIMPLE WAY TO REMEMBER

Newbert can serve public images, CSS, JavaScript, and downloadable static assets via a CDN while its API remains separately hosted.

ADDED ENGINEERING DETAIL

A CDN does not automatically cache every authenticated HTML/API response. Private data needs explicit cache policy.

X/Twitter trends: cache heavy computation

FROM THE LESSON

The teacher explains how detecting trends from huge numbers of posts is costly. A system can compute a snapshot periodically and serve the saved result to many users rather than re-running analytics for every page load.

  • A cached trends list is a materialized, precomputed answer to an expensive question.
  • The lecturer mentions a few minutes as an illustrative update interval, not a verified description of X internals.
  • Best fit: high read volume, expensive computation, change rate slower than read rate.
SIMPLE WAY TO REMEMBER

For Newbert, update “Top internships this week” at intervals rather than running aggregation on every dashboard visit.

ADDED ENGINEERING DETAIL

A short TTL is not a substitute for correctness when prices, eligibility, or deadlines require real-time accuracy.

Three layers: network, hardware, software

FROM THE LESSON

The instructor groups backend-relevant caches into network-level, hardware-level, and software-level caching. All aim to reduce the distance or cost between the requester and useful data.

  • Network: CDNs and DNS caching.
  • Hardware: CPU cache hierarchy (L1/L2/L3) and RAM.
  • Software: Redis/Memcached and application-level cache libraries, usually running on memory-backed hardware.
SIMPLE WAY TO REMEMBER

Ask three questions: Is network travel expensive? Is memory access expensive? Is an application computation or database query expensive?

ADDED ENGINEERING DETAIL

These layers are related but different; caching API JSON in Redis will not magically accelerate CPU-bound code.

How a CDN request actually travels

FROM THE LESSON

Browser resolves a hostname; CDN routing steers the request toward a suitable Point of Presence (PoP). The edge checks for a local copy. On a hit, it serves from edge. On a miss, it obtains content from an origin or upstream cache and stores it subject to caching rules.

  • A PoP is a regional deployment of edge infrastructure.
  • TTL (time to live) determines how long a cache entry remains fresh, depending on cache rules.
  • When an asset changes, a versioned filename or purge/invalidation avoids old assets being served.
SIMPLE WAY TO REMEMBER

If a JavaScript file changes, assets named app.abc123.js are easier to cache safely than a permanent app.js URL.

ADDED ENGINEERING DETAIL

CDN routing is based on network topology, health, capacity, and policies; geographically closest is not always best.

DNS: resolve a name without repeating all lookups

FROM THE LESSON

A DNS resolver can answer a familiar domain from a cached record. Otherwise it may consult root hints, root DNS, top-level-domain servers, and an authoritative nameserver. Each successful lookup can be reused until its DNS TTL expires.

  • Domain → IP address is one common DNS task (A/AAAA records).
  • Recursive resolvers frequently cache records to avoid repeating full delegation lookups.
  • Operating systems and browsers may also cache DNS results; exact lookup order differs by platform.
SIMPLE WAY TO REMEMBER

Imagine Newbert.in is a friend’s saved phone number: when saved, you avoid asking multiple people for the number each time.

ADDED ENGINEERING DETAIL

Root DNS has 13 named root-server identities but many globally distributed instances; avoid interpreting that as only 13 physical machines.

CPU caches, RAM and SSD: why memory speed matters

FROM THE LESSON

The video moves from CPU L1/L2/L3 caches to RAM and secondary storage. Hot data near processing units avoids slow repeated fetches from lower levels. Redis and Memcached primarily keep active data in RAM.

  • L1 tends to be very small and very fast; L2 is larger; L3 may be shared among cores; RAM is larger and farther from CPU.
  • Sequential array traversal often exploits spatial locality and cache lines.
  • RAM usually loses its contents without power. SSDs retain data, but are a separate tier.
SIMPLE WAY TO REMEMBER

Think: pocket note → desk notebook → shelf → distant library. Nearby is typically faster but capacity is smaller.

ADDED ENGINEERING DETAIL

Redis can optionally persist snapshots or an append-only log to disk; Memcached generally does not provide durable storage.

Redis, Memcached and ElastiCache

FROM THE LESSON

The instructor names Redis, Memcached and AWS ElastiCache as examples of systems commonly used for RAM-backed key/value operations. Instead of querying relational rows, the application retrieves a value via its key.

  • Redis supports multiple data structures, expirations, and atomic operations.
  • Memcached emphasizes simple distributed in-memory caching.
  • Amazon ElastiCache is a managed caching service, not a distinct key/value data model.
SIMPLE WAY TO REMEMBER

Key: `internships:category:backend` → Value: serialized response data.

ADDED ENGINEERING DETAIL

A cache is not the system of record by default. Always plan for cache failure or loss.

Cache-aside vs write-through

FROM THE LESSON

The instructor contrasts lazy caching (cache-aside) with write-through. In cache-aside, reads first check cache, then DB on a miss. In write-through, mutation flows update the backing data store and cache as part of the write path.

  • Cache-aside: GET → cache miss → DB → SET cache with TTL → return.
  • Write-through: mutation updates stored truth and cached copy together in the write workflow.
  • Cache invalidation: after changes, delete the affected cache key or update it carefully.
SIMPLE WAY TO REMEMBER

In Newbert, GET /api/jobs/featured can cache-aside; PATCH /api/jobs/:id should invalidate dependent featured-list keys.

ADDED ENGINEERING DETAIL

Two independent writes are not automatically atomic. A failed cache update can still leave stale data; a transaction or reliable invalidation strategy matters.

11
TEACHER'S SEQUENCE · 45:19–51:13 ↗

Eviction: when memory is full

FROM THE LESSON

Because RAM is finite, a cache needs a policy for what to discard when it reaches its memory budget. The teacher covers no eviction, LRU, LFU, and TTL-aware eviction.

  • No eviction: may reject writes when maxmemory is reached.
  • LRU = least recently used; remove the entry with the oldest use.
  • LFU = least frequently used; remove a low-frequency entry.
  • TTL-aware eviction = favor entries with soonest expiration among eligible keys; expiration and eviction are distinct events.
SIMPLE WAY TO REMEMBER

If internship A was requested yesterday and B ten times today, LRU and LFU may produce different victims depending on use history.

ADDED ENGINEERING DETAIL

Redis `volatile-ttl` considers only expiring keys. Its LRU/LFU implementations are approximations, and expiration does not necessarily occur at the exact nanosecond of TTL expiry.

Four real backend use cases

FROM THE LESSON

The teacher’s practical set is database query caching, session storage, external API response caching, and rate limiting. A cache can save slow joins/aggregations, keep session lookups fast, reduce paid third-party API calls, and count requests cheaply.

  • Database: cache popular product/profile/listing query results that change relatively slowly.
  • Sessions: store server-side session data indexed by a high-entropy session identifier.
  • External API: cache weather responses for a sensible window, honoring upstream restrictions.
  • Rate limiter: increment a per-user/IP counter with expiration; return 429 when the threshold is exceeded.
SIMPLE WAY TO REMEMBER

Newbert: cached job-list pages, login sessions (if session-based), GitHub API result caching, and an abuse-resistant /api/search limit.

ADDED ENGINEERING DETAIL

Use trusted proxy configuration before reading forwarded IP headers. Rate-limit keys must not rely on user-controlled X-Forwarded-For values.

Additional practice · beyond the video

Build the same architecture with Express + Redis + PostgreSQL

This is a small guided implementation for Newbert. Step 1: Install Node.js, Redis and PostgreSQL. Step 2: Run npm init -y, set "type":"module" in package.json, and run npm install express redis pg. Step 3: Create a sample jobs(id, title, company, featured) table and set DATABASE_URL and REDIS_URL. Step 4: Save this as server.js and run node server.js.

Starter SQL for your local PostgreSQL database:

CREATE TABLE IF NOT EXISTS jobs (
  id SERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  company TEXT NOT NULL,
  featured BOOLEAN NOT NULL DEFAULT FALSE
);
INSERT INTO jobs (title, company, featured) VALUES
  ('Backend Intern', 'Startup Alpha', TRUE),
  ('Node.js Intern', 'Startup Beta', TRUE);

Express/Redis implementation:

// package.json: {"type":"module"}
// npm install express redis pg
import express from "express";
import { createClient } from "redis";
import pg from "pg";

const app = express();
app.use(express.json());
const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
const cache = createClient({ url: process.env.REDIS_URL || "redis://localhost:6379" });
cache.on("error", err => console.error("Redis:", err.message));
await cache.connect();

// This demo assumes you created a jobs table in PostgreSQL.
// Production: validate input and implement authentication/authorization.
app.get("/api/jobs/featured", async (req, res, next) => {
  const key = "jobs:featured:v1";
  try {
    let saved = null;
    try { if (cache.isReady) saved = await cache.get(key); }
    catch (error) { console.warn("Cache read failed; using DB"); }

    if (saved !== null) {
      res.set("X-Cache", "HIT");
      return res.json(JSON.parse(saved));
    }

    const { rows } = await pool.query(
      "SELECT id, title, company FROM jobs WHERE featured = TRUE ORDER BY id DESC LIMIT 20"
    );
    try { if (cache.isReady) await cache.set(key, JSON.stringify(rows), { EX: 60 }); }
    catch (error) { console.warn("Cache write failed; using DB result"); }
    res.set("X-Cache", "MISS");
    res.json(rows);
  } catch (error) { next(error); }
});

// Invalidate AFTER a successful database mutation.
app.patch("/api/jobs/:id", async (req, res, next) => {
  try {
    // Demo simplification: only featured is editable; real code requires auth.
    if (typeof req.body.featured !== "boolean")
      return res.status(400).json({ error: "featured must be boolean" });
    const { rows } = await pool.query(
      "UPDATE jobs SET featured=$1 WHERE id=$2 RETURNING id, title, featured",
      [req.body.featured, req.params.id]
    );
    if (!rows.length) return res.sendStatus(404);
    try { if (cache.isReady) await cache.del("jobs:featured:v1"); }
    catch (error) { console.error("Invalidation failed:", error.message); }
    res.json(rows[0]);
  } catch (error) { next(error); }
});

app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: "Internal server error" });
});
app.listen(3000, () => console.log("http://localhost:3000"));

Important limitations: This demonstrates the basic flow, not a production-ready mutation endpoint. Add authentication, ownership checks, full validation, protected secrets, telemetry, and reliable invalidation. If Redis becomes unavailable after startup, reads fall back to PostgreSQL when the client is not ready; if cache deletion fails after a write, the old cached value can be served until TTL expires.

Extra insight · professional checklist

Five mistakes to avoid when adding caching

  1. Never cache personalized responses under a shared key. Include relevant user/tenant scope and enforce private cache headers.
  2. Do not assume TTL makes data correct. An entry can be stale for all 60 seconds until expiry. Use invalidation when necessary.
  3. Do not trust forwarded client-IP headers by default. Configure trusted reverse proxies before deriving client identity.
  4. Do not treat RAM as persistent by default. Plan for cache restart, eviction and recovery.
  5. Do not blindly cache high-cardinality queries. Low repeat use may cost more memory and overhead than it saves.
