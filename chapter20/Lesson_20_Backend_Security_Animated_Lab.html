One lesson, one mental model

Security bugs arise where we incorrectly trust something: a user's text is treated as SQL; a session is treated as proof of permission; HTML content is treated as safe code.

Untrusted input
Verify shape
Verify identity
Verify access
Safe operation
REMEMBER: Don't trust UI input. Don't trust guessed IDs. Don't trust unverified tokens.

🧩 Teacher's point

Attackers search for developers' assumptions. The defense begins by identifying those assumptions.

🧠 Easy example

Changing /applications/41 to /applications/42 must not reveal another student's record.

🍪 Server session
Cookie holds an opaque ID. The server stores which user that ID belongs to, plus the expiry. Delete a session record to revoke it.
🪪 JWT
Header.payload.signature. Payload is readable, signature protects integrity. A purely stateless token can remain valid until expiry even after you ask to log out.

SIMULATOR 04
Authorization: who can access what?
The teacher distinguishes BOLA (the wrong object's data) from BFLA (the wrong privileged function). Test both.
Choose a user, record, and operation; then check.
BOLA: You are a logged-in user but try to read another user's private record.
The safe database query scopes by record ID and trusted authenticated owner ID.
BFLA: Your role does not permit calling an administrative function.
Hiding /admin is not a role check. Deny by default.


SIMULATOR 05
Cookies, XSS and CSRF
See the difference between a page reading a cookie and a cross-site request using a cookie automatically.
Choose defenses
XSS prevention
Render untrusted text safely. If you must render user HTML, sanitize with a vetted library. Set a restrictive CSP for extra protection.
CSRF prevention
SameSite reduces cross-site cookie exposure. Sensitive cookie-authenticated actions may also require CSRF tokens, Origin checks, or framework protections. CORS by itself is not enough.
