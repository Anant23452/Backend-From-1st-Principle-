Experiment 2 — read the file without fear

Every section of OpenAPI answers one question

Read this as a story: What API is it? Where is it? Which route do I call? What do I send? What comes back? Select any concept to highlight its meaning.

openapi: 3.1.0
info:
  title: Newbert API
  version: 1.0.0
servers:
  - url: http://localhost:5000
paths:
  /applications:
    post:
      summary: Apply for an internship
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [internshipId]
              properties:
                internshipId: { type: string }
      responses:
        '201':
          description: Application created

Important distinction: openapi: 3.1.0 is the standard version; info.version: 1.0.0 is Newbert's API version.
Experiment 3 — change the request body

What does a Schema Object actually do?

A form looks correct to Rahul, but the API receives text over the internet. The contract says internshipId is required and must be a non-empty string. Type different JSON and check the result.
{
  "type": "object",
  "required": ["internshipId"],
  "properties": {
    "internshipId": {
      "type": "string",
      "minLength": 1
    }
  }
}
Change the JSON and press Validate.
🧠 A schema describes allowed data. The production backend needs actual runtime validation to enforce it.

Experiment 5 — pipeline stepper

Design-first, one step at a time

Think of OpenAPI as the agreed building plan. The team checks the plan, uses it to simulate the building, generates helpful measurements, constructs the real backend, then tests that the building matches its plan.

Step 1 of 6 — Design the API contract.
🧠 Tools mentioned in the lesson include Spectral (lint), Prism (mock), code generators and Schemathesis (tests). Their support for each OpenAPI version varies.
