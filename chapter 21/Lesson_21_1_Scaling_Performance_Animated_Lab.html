TEACHER'S MAIN LESSON

A fast system is not merely one with a fast database. It must respond predictably under real traffic, including bursts and complex user actions. The talk builds intuition before scaling techniques, not the other way around.

ADDITIONAL INSIGHT Measure the user's total interaction latency separately from Express server time. The browser's network delay and rendering time matter too.

02 · Ice cream queues and utilization

ICE CREAM SHOP + HIGHWAY

At low utilization, the worker serves you quickly. With more visitors, the worker can still make ice cream at the same speed, but waiting increases. The same happens to a capacity-limited backend.

Utilization-
Estimated response-
Headroom-

Important correction

A simple queue model is:

Response time ≈ 1 / (μ - λ)
μ = service capacity
λ = arrival rate
Valid when λ < μ

Our simulator uses this idealized M/M/1 model. Real Node.js services have multiple resources, worker pools, network waits and variable job sizes.

HeadroomUnused capacity saved for sudden traffic bursts. The teacher suggests retaining spare resources, not running constantly at 100%.
BurstMany requests arriving close together - e.g. a viral Newbert internship alert.

03 · Don't guess the bottleneck

TEACHER'S SLOW PRODUCT ENDPOINT

The team first suspects PostgreSQL and adds Redis, but response time barely improves. The real problem is synchronous remote logging. Try different root causes and inspect the timings.

ComponentDurationApprox. share

Profiler or distributed trace?

CPU profilerShows which JavaScript functions consume CPU cycles; flame graphs visualize hot call stacks.
Distributed tracingTracks a request's spans across Express, databases and third-party services. Great for seeing slow waits.
SpanA timed operation such as SELECT jobs, JWT verification or HTTP request to an email API.
Modern profiling can capture more than CPU, depending on tool. Use both tracing and profiling when necessary.

Terms you'll use in interviews

B-treeBalanced ordered index; search normally scales roughly with log(n), not O(1).
Composite indexIndex on ordered columns, e.g. (user_id, created_at).
Covering indexStores enough selected values that an index-only scan may be possible.

Three patterns

Cache-asideApplication checks cache and fills it on a miss.
Write-throughWrite-through implementation updates cache and DB as part of a coordinated write path.
Write-behindWrites are buffered first and persisted to DB later, needing strong durability controls.
TTLTime to live: an expiry window for a cached item.
Higher cache hit ratio is not always better if it causes harmful stale reads or masks expensive misses.

08 · Scale up or scale out?

VERTICAL VS HORIZONTAL SCALING

Trade-offs matter

Scale upStronger CPU, more RAM, faster storage. Easier architecture; finite hardware and single-host failure risk.
Scale outMore replicas behind a load balancer. Needs coordinated state, DB capacity and health checks.
Capacity increases shown here are idealized. More instances do not guarantee proportionally more throughput if PostgreSQL or an external API is saturated.
